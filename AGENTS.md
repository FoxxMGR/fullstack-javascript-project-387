# AGENTS.md — инструкции для ИИ-агента (OpenCode / Cline)

Этот репозиторий развивается через агентский процесс: issue → triage → PR →
ревью (человек) → правки в той же ветке → мерж → релиз (release-it).
Агент работает как ассистент человека: предлагает решения и реализует их,
решения о слиянии принимает человек.

## Как устроен проект

| Каталог    | Назначение                                                    |
| ---------- | ------------------------------------------------------------- |
| `api-spec` | Контракт API (TypeSpec → OpenAPI). Всё API живёт по нему      |
| `server`   | Бэкенд Node.js + TypeScript, хранилище в памяти, без внешних зависимостей |
| `web`      | Фронтенд (React + Vite), работает с API только по контракту   |
| `e2e`      | Интеграционные тесты Playwright (прокси 5173 → 8080)          |

## Как поднять проект

```bash
# Бэкенд (порт 8080)
cd server && npm install && npm start

# Фронтенд (порт 5173), в другом терминале
cd web && npm install && npm run dev
# Открыть http://localhost:5173 (вкладки «Гость» и «Владелец»)
```

Проверка типов бэкенда: `cd server && npm run check` (это `tsc --noEmit`).

## Как запускать e2e

```bash
cd e2e && npm ci && npx playwright install --with-deps chromium && npx playwright test
```

e2e ходят через прокси Vite (`http://localhost:5173`), поэтому перед прогоном
должны быть подняты и `server`, и `web`. Тесты — в `e2e/tests/*.spec.ts`.

## Правило Conventional Commits (обязательно)

Каждый коммит агента — по спецификации
[Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <заголовок до 100 символов>

<body: причина изменения>
```

Допустимые `type`: `feat`, `fix`, `docs`, `refactor`, `test`, `ci`,
`chore`, `style`, `build`, `perf`, `revert`. `scope` — например, `server`,
`web`, `e2e`, `api-spec`, `ci`. Проверяется `commitlint` в CI
(`.github/workflows/commitlint.yml`) — коммиты не по формату роняют PR.

Примеры:
- `fix(server): ограничить диапазон дат в /guest/availability`
- `test(e2e): покрыть отказ при слишком большом диапазоне дат`
- `feat(web): форма ввода токена админки`

## Контракт API

Любое изменение эндпоинта начинается с `api-spec/main.tsp` (TypeSpec).
Сервер реализует ровно то, что описано в контракте; фронтенд ходит только по
`/guest/*` и `/admin/*`. Меняете поведение — сначала правьте контракт, затем
сервер, затем тесты.

## Шаблон triage-комментария в issue

Отвечая на issue, агент пишет:
- что происходит сейчас (воспроизведение/диагноз);
- оценка (объём, затронутые файлы);
- план реализации или вопрос-уточнение;
- при готовности — предложение «/oc fix this» для подготовки PR.

## Порядок работы над задачей

1. Понять задачу из issue и критерии приёмки (в шаблоне issue).
2. Сделать triage-комментарий.
3. Подготовить ветку `fix/<slug>` / `feat/<slug>` и PR, связанный с issue
   (closes #<номер>).
4. Каждый коммит — по Conventional Commits.
5. На замечания ревью отвечать правками в **той же** ветке, новыми коммитами.
6. Не мержить и не одобрять PR самостоятельно.

## Ограничения

- Никаких API-ключей, токенов и секретов в репозиторий и логи.
- Не удалять и не редактировать `.github/workflows/hexlet-check.yml`
  (генерируется и используется тестами Hexlet).
