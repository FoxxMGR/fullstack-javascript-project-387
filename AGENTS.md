# AGENTS.md — инструкции для ИИ-агента (OpenCode / Cline)

Этот репозиторий развивается через агентский процесс: issue → triage → PR →
ревью (человек) → правки в той же ветке → мерж → релиз (release-it).
Агент работает как ассистент человека: предлагает решения и реализует их,
решения о слиянии принимает человек.

## Как устроен проект

| Каталог    | Назначение                                                    |
| ---------- | ------------------------------------------------------------- |
| `api-spec` | Контракт API (TypeSpec → OpenAPI). Всё API живёт по нему      |
| `server`   | Бэкенд Node.js + TypeScript, хранилище в памяти, без внешних зависимостей |
| `web`      | Фронтенд (React + Vite), работает с API только по контракту   |
| `e2e`      | Интеграционные тесты Playwright (прокси 5173 → 8080)          |

## Как поднять проект

```bash
# Бэкенд (порт 8080)
cd server && npm install && npm start

# Фронтенд (порт 5173), в другом терминале
cd web && npm install && npm run dev
# Открыть http://localhost:5173 (вкладки «Гость» и «Владелец»)
```

Проверка типов бэкенда: `cd server && npm run check` (это `tsc --noEmit`).

## Как запускать e2e

```bash
cd e2e && npm ci && npx playwright install --with-deps chromium && npx playwright test
```

e2e ходят через прокси Vite (`http://localhost:5173`), поэтому перед прогоном
должны быть подняты и `server`, и `web`. Тесты — в `e2e/tests/*.spec.ts`.

## Правило Conventional Commits (обязательно)

Каждый коммит агента — по спецификации
[Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <заголовок до 100 символов>

<body: причина изменения>
```

Допустимые `type`: `feat`, `fix`, `docs`, `refactor`, `test`, `ci`,
`chore`, `style`, `build`, `perf`, `revert`. `scope` — например, `server`,
`web`, `e2e`, `api-spec`, `ci`. Проверяется `commitlint` в CI
(`.github/workflows/commitlint.yml`) — коммиты не по формату роняют PR.

Точные требования `commitlint` (любое нарушение = красный PR):
- заголовок ≤ 100 символов и начинается с `<type>(<scope>): `;
- subject в **нижнем регистре** (нельзя «DatePicker: …», «LH: …»,
  «Fix …») и без точки в конце;
- строки body ≤ 100 символов, между отсутствуют footer-блоки.

Перед пушем проверить локально, что коммиты чистые:

```bash
npx commitlint --from "<sha-base>" --to HEAD --verbose
```

Примеры:
- `fix(server): ограничить диапазон дат в /guest/availability`
- `test(e2e): покрыть отказ при слишком большом диапазоне дат`
- `feat(web): форма ввода токена админки`

## Контракт API

Любое изменение эндпоинта начинается с `api-spec/main.tsp` (TypeSpec).
Сервер реализует ровно то, что описано в контракте; фронтенд ходит только по
`/guest/*` и `/admin/*`. Меняете поведение — сначала правьте контракт, затем
сервер, затем тесты.

## Шаблон triage-комментария в issue

Отвечая на issue, агент пишет:
- что происходит сейчас (воспроизведение/диагноз);
- оценка (объём, затронутые файлы);
- план реализации или вопрос-уточнение;
- при готовности — предложение «/oc fix this» для подготовки PR.

## Порядок работы над задачей

1. Понять задачу из issue и критерии приёмки (в шаблоне issue).
2. Проверить открытые issues и PR на дубли: если фича уже реализована или
   частично готова в открытом PR — не писать новую реализацию «с нуля»,
   а продолжить существующую (см. Definition of Done).
3. Сделать triage-комментарий.
4. Подготовить ветку `fix/<slug>` / `feat/<slug>` и PR, связанный с issue
   (closes #<номер>).
5. Каждый коммит — по Conventional Commits.
6. На замечания ревью отвечать правками в **той же** ветке, новыми коммитами.
7. Не мержить и не одобрять PR самостоятельно.

## Definition of Done — пройти перед пушем/PR

Каждый PR агента обязан проходить **все** проверки репозитория (commitlint,
e2e, hexlet-check); красный PR считается не готовым. Чек-лист перед пушем:

1. **Коммиты** — все по Conventional Commits; проверено
   `npx commitlint --from "<base>" --to HEAD --verbose` (0 проблем).
2. **e2e** — если меняются фронтенд, разметка, шаги UI, тексты/селекторы или
   API — `e2e/tests/*.spec.ts` ОБЯЗАТЕЛЬНО адаптированы в этом же PR, набор
   прогнан локально (`cd e2e && npx playwright test`). Красные e2e недопустимы.
3. **Типы** — `npm --prefix server run check` и `npm --prefix web run lint`
   проходят без ошибок.
4. **Контракт** — изменение поведения эндпоинта меняет `api-spec/main.tsp`
   первым; сервер и тесты — следом.
5. **Нет дублей** — PR не копирует фичу из другого открытого PR/issue.
6. **Чистый дифф** — без артефактов и сгенерированных больших файлов
   (отчёты Lighthouse, логи, `dist/`, бандлы, скриншоты).
7. **Название PR** повторяет subject главного коммита.

## Ограничения

- Никаких API-ключей, токенов и секретов в репозиторий и логи.
- Не удалять и не редактировать `.github/workflows/hexlet-check.yml`
  (генерируется и используется тестами Hexlet).

## Воркфлоу в репозитории и переменные

Агентских воркфлоу три (детали и таблица — в README.md):

- `opencode` — интерактивный вызов по команде `/oc` / `/opencode` в
  комментариях issue и PR. Автор комментария должен быть в списке
  `AGENT_ALLOWED_AUTHORS` (Variables → переменная репозитория, через запятую).
  Права на запись есть, поэтому агент может создавать ветки, коммиты и PR.
- `auto-review` — авторевью каждого `pull_request` (opened/synchronize/
  reopened/ready_for_review). Только чтение; замечания — комментарием.
- `night-check` — ночной Lighthouse-аудит по расписанию. Для работы нужна
  переменная репозитория `APP_URL` (публичный адрес приложения) и секрет
  `OPENCODE_API_KEY`. Создаёт issue с итогами, в код не пишет.

Переменные, которые ожидает воркфлоу (Settings → Secrets and variables →
Actions → Variables): `AGENT_ALLOWED_AUTHORS`, `APP_URL`. Секретов требуется
один — `OPENCODE_API_KEY`.
