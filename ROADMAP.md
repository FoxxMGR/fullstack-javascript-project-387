# ROADMAP — план развития «Календаря звонков»

Приложение перенесено из проекта 386. Дальше продукт развивается через
агентский процесс: каждая задача ниже заводится как issue, агент делает
triage в комментариях и PR, ревью — человек.

Приоритет: **P0** — берём первыми (хороший материал для triage), **P1** —
далее, **P2** — по остаточному принципу. Метки: `bug`, `feature`, `ci`.

## Баги (исправляет агент)

### BUG-1 · Слоты зависят от таймзоны сервера · `bug` `P0`
`server/src/slots.ts` генерирует рабочее окно 09:00–18:00 в локальной таймзоне
сервера (`new Date(y, m, d, WORK_START_HOUR)`), а фронтенд показывает время в
таймзоне гостя (`web/src/lib/format.ts`). На Render сервер живёт в UTC, поэтому
гость в Москве видит окно 12:00–21:00, а бронирование в 17:00 UTC «попадает»
в 20:00 МСК.
**Критерии:** рабочее окно фиксировано в явной таймзоне (константа/env, по
умолчанию UTC), гости видят корректное время независимо от региона сервера;
добавлены юнит/e2e-проверки на границе дня.

### BUG-2 · `/guest/availability` не ограничивает диапазон дат · `bug` `P0`
`getAvailableSlots` (`server/src/app.ts`) принимает любые `dateFrom`–`dateTo`:
запрос на 10 лет заставляет `generateSlots` построить сотни тысяч слотов —
медленный ответ и лишняя нагрузка (потенциальный DoS).
**Критерии:** диапазон больше N дней (например, 60) → `400 RANGE_TOO_LARGE`;
есть тест на отказ и на пограничное значение.

### BUG-3 · Создание ресурсов отвечает `200` вместо `201` · `bug` `P1`
`POST /guest/bookings` и `POST /admin/event-types` возвращают `200`.
**Критерии:** оба эндпоинта возвращают `201 Created`, обновлены e2e-тесты и
контракт в `api-spec/main.tsp`, CHANGELOG фиксирует breaking-free изменение.

### BUG-4 · Дубликаты типов событий · `bug` `P2`
Владелец может создать сколько угодно типов с одинаковым `title` и
`durationMinutes` — список засоряется, гость путается.
**Критерии:** полное совпадение → `409 EVENT_TYPE_EXISTS`; UI показывает
понятную ошибку; тест в e2e.

## Фичи (реализует агент)

### FEAT-1 · Авторизация владельца для `/admin/*` · `feature` `P0`
Сейчас админское API открыто всем: любой может создавать типы событий и
отменять брони (`server/src/app.ts`), CORS — `*`.
**Критерии:** токен из env `ADMIN_TOKEN` (заголовок `Authorization: Bearer`),
`401/403` без него; гость не затронут; в админке — форма ввода токена;
секрет не попадает в репозиторий и логи.

### FEAT-2 · Отмена брони гостем по секретной ссылке · `feature` `P1`
Отменить бронирование может только владелец (`DELETE /admin/bookings/:id`).
**Критерии:** при создании брони генерируется cancel-токен, гостю показывается
ссылка; `DELETE /guest/bookings/:id?token=...` отменяет бронь; токен одноразовый
и не раскрывает чужие брони; e2e-тест сценария.

### FEAT-3 · Настраиваемые рабочие часы · `feature` `P1`
Окно Пн–Пт 09:00–18:00 захардкожено в `server/src/slots.ts`
(`WORK_START_HOUR`/`WORK_END_HOUR`).
**Критерии:** владелец задаёт окно и рабочие дни в админке (хранятся в store);
валидация пересечения с существующими бронями; слоты строятся по настройке.

### FEAT-4 · Экспорт расписания в ICS · `feature` `P2`
`GET /admin/bookings.ics` отдаёт файл календаря с предстоящими встречами;
кнопка «Скачать .ics» в админке.

### FEAT-5 · Персистентность хранилища · `feature` `P2`
Данные живут в памяти и сбрасываются при перезапуске (`server/src/store.ts`).
Опциональное JSON/SQLite-хранилище через env `STORAGE=file|memory`,
демо-сид сохраняется для dev.

## Инфраструктура и процесс (цель этого проекта)

### CI-1 · OpenCode GitHub App · `ci` `P0`
Установить OpenCode GitHub App на репозиторий, проверить, что агент отвечает
в issue и умеет открывать PR. Завести issues из этого ROADMAP (метки выше).

### CI-2 · Ночной Lighthouse по расписанию · `ci` `P0`
`.github/workflows/lighthouse.yml` с `schedule:` (ночью): сборка `web`,
прогон Lighthouse CI на десктопе и мобиле, отчёт — артефакт; при падении
порогов (Performance < 90 и т.п.) — issue/комментарий с результатом.

### CI-3 · Инструкции для агента · `ci` `P1`
`AGENTS.md`: как поднять проект, как запускать e2e, правила Conventional
Commits, требование идти по контракту `api-spec`, шаблон triage-комментария.

## Порядок запуска задач

1. CI-1 → issues из ROADMAP → BUG-1 (triage + PR агента).
2. BUG-2 → FEAT-1 → CI-2 (к этому моменту есть деплой для Lighthouse).
3. BUG-3, FEAT-2, FEAT-3 — далее по очереди, по одному PR на задачу.
